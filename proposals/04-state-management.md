# State Management

Today: Pinia, with `useGameStore` (`src/ui/stores/game.ts`) holding a `TitanGame` value in `reactive()` — the store state *is* that value, and the nested `Battle` value (`TitanGame.activeBattle`) inherits the same reactive proxying as a field on it. `TitanGame`, `Stack`, `BattleCreature`, `ActiveStrike`, and `Battle` are plain interfaces with their logic in `namespace`-scoped free functions, not classes: `TitanGame.hydrate(persisted?: string)` takes the persisted JSON string as a parameter and merges it onto a fresh `TitanGame.create(2)`; persistence itself lives in the store, not the model layer (doc 05). Every action is a single assert-then-mutate free function (`move`, `setRecruit`, `nextPhase`, `moveCreature`, `attackCreature`, ...) — the old `do*`/`m*` pairing is gone entirely — while query functions keep `get*`/`is*`/`can*` naming; the store defines explicit typed getters and actions directly, with no reflection or naming-based dispatch.

## Game state has been separated from game rules

`TitanGame` used to mix serializable state (players, stacks, round) with rules logic (pathfinding, mustering, battle resolution) in one class graph, with reactive proxies wrapping the class instances. That conversion is done: `Stack`, `BattleCreature`, `ActiveStrike`, `Battle`, and `TitanGame` are now plain interfaces plus free functions, each converted in its own PR, one class per PR in dependency order — `Stack` first (thin; `Player` was already a plain interface with no hydrate glue), then `BattleCreature` and `ActiveStrike`, then `Battle` and `TitanGame` last. Each step converted one class to an interface plus free functions and deleted its hydrate glue; no production code did `instanceof` on a state class, so nothing structurally resisted the conversion.

Vue's reactivity works on plain objects without proxy-vs-class pitfalls, the rules run identically on a server (doc 05), and the per-class `hydrate` methods are gone. The state tree was already effectively serializable plain data going in — every stateful field on `TitanGame`, `Player`, `Stack`, `Battle`, `BattleCreature`, and `ActiveStrike` is a number, enum, boolean, array, or `Record`; entities reference board positions by hex number, never by object; and the masterboard, battle boards, creature stats, and muster tables are static module data outside the state graph. (`JSON.stringify` of a game works today for exactly this reason.) The conversion was "detach the methods," not "re-model the state."

**`Battle` nested inside `TitanGame` is not the problem, and the nesting earns its keep.** Nothing outside `TitanGame` looks up a `Battle` independent of `game.activeBattle`: there's no separate battle store, and every battle component reaches it that way. Persistence is one `JSON.stringify(game)` call in `useGameStore`'s watcher, so `Battle` round-trips with the rest of the tree instead of needing its own save/load wiring. Doc 05's dispatch model doesn't push toward a flat shape either — it resolves entities by id from whatever tree holds them, so nesting costs it nothing.

`activeBattle` is a single field today rather than a keyed collection, but that's not a settled property of the domain to credit as a design win: `nextPhase` asserts `engagedStacks.length <= 1` only because no UI yet lets a player choose which of 2+ simultaneous engagements to resolve first (`nextPhase`'s TODO in `game.ts`), and the game's rules permit concurrent battles. If that ships, `activeBattle` becomes an array or map regardless of nesting, and a keyed collection would have been the natural shape from the start — a real cost, but one worth paying only once multi-engagement support is real, not preemptively for the single-battle case that holds today.

The discomfort used to trace to reactive-proxy nesting friction: `BattleCreature` sat two proxy levels deep (`TitanGame` → `activeBattle` → `creatures[]`), and Vue's `UnwrapNestedRefs` couldn't reconstruct class-private members, forcing a cast back to the class type in `BattleBoard.vue`. That cast is gone now that `BattleCreature` is a plain interface. `Battle` (`battle/engine.ts`, ~590 lines) is still the largest file in the model layer, bigger than `TitanGame` (`game.ts`, ~341 lines) — but that reflects the size of battle rules themselves, not the nesting: every one of `Battle`'s functions operates on `Battle`'s own state, with nothing reaching back into `TitanGame`.

The plain-data conversion removed that friction, so extracting `Battle` into a sibling state tree was never worth doing as its own slice: the friction lived in having class instances inside reactive proxies at all, and structural surgery on them would have hit that friction head-on instead of removing it. Now that state is plain data, "field on `TitanGame` or sibling tree" is a nearly-free choice either way.

**Storing a `PlayerId` and resolving it through `getPlayerById` everywhere is the right pattern — keep it.** `Stack.owner`, `BattleCreature.player`, and `Battle`'s `attacker`/`defender` all hold a `PlayerId`, and rendering anything player-flavored (name, color, score) resolves it through `getPlayerById`, a linear `find` over `game.players`. The lookup frequency reflects the domain — nearly everything on screen renders in its owner's color — not a design smell, and the scan cost is unmeasurable: `TitanGame.create` caps the game at five players (colors, not `INITIAL_HEXES`, are the binding limit), and the UI call sites are `computed`s or per-render template bindings either way iterating a ≤5-element array. A `Map<PlayerId, Player>` or memoized `Record` would add indirection with no observable win at this scale. Call-site count isn't fully fixed by the domain, though: some resolves were passthrough ceremony from a child component's prop type demanding a `Player` rather than a `PlayerId`, and pushing the id prop down to the leaf and resolving only where needed cut `Creature.vue`'s call sites roughly in half (8 → 4); score's move off `Player` above removed the rest, so `Creature.vue` calls it zero times today.

The id reference is also load-bearing for everything else in this doc: snapshot persistence works precisely because entities carry ids rather than object references, and `TitanGame.hydrate` builds fresh `Stack`s independently via `TitanGame.create` before the persisted data is merged on top (`Player` needs no reconstruction — it's already plain data) — a denormalized `Player` reference stored on `Stack` would sever on every restore and need explicit re-linking, recreating the object-identity fragility doc 05's still-pending actions-as-data slice aims to remove (that slice moves action *payloads* from live instances to ids; the entity fields already carry ids). One existing counterexample shows the alternative's cost: `BattleCreature.playerScore` is a *copy* of the owner's score taken at battle initiation, and like any copy it has implicit staleness semantics the id reference doesn't. Under the plain-data conversion, `getPlayerById` is now one of the free selector functions in `TitanGame`; nothing about the pattern changed.

**`Player`'s three fields belong in `TitanGame`, but for different reasons:**

- `score` is rules state and must stay in the state graph — it has moved off `Player` onto `TitanGame` (`score: Record<PlayerId, number>`). It feeds titan combat strength (`getStrength`: 6 + score/100, via the `playerScore` snapshot) and titan tower-teleport eligibility (`canTitanTeleport`). Nothing mutates it yet — end-of-battle scoring is still the parked work doc 05 notes — but once scoring lands, score changes on battle resolution and must replay from the action log.
- `id` is the seat, and a game concept: the `PlayerId` enum doubles as the color, shuffle-assigned at game creation, keying marker art, theming (`bg-player-${id}`), and every entity's owner field.
- `name` is the one roster field: written once in `TitanGame.create` (`Player ${i + 1}`), never read by rules, only displayed. Under doc 05's authoritative-server model, "who occupies seat X" — display name, account, connection — is session state the server tracks beside the game, resolved by the same `PlayerId`.

The eventual multiplayer refinement is that `Player` slims to seat-keyed rules state while `name` migrates to the roster — not that id lookups go away.

## Replace localStorage snapshot persistence with an action log (not urgent)

Persisting a snapshot works for solo play but discards history. If actions become explicit data (doc 05's still-pending dispatch slice), persistence could become "store the action log, replay to restore" — which also gives undo and post-game review nearly for free. Snapshot persistence has already moved out of the rules layer into the store (doc 05's first groundwork slice, now done: a deep `watch` on the reactive `game` proxy in `src/ui/stores/game.ts` writes `JSON.stringify(game)` to `localStorage` on every mutation); an action log would replace that store-side persistence — there's no rules-layer persistence code left for it to replace.

- **Pros:** aligns local persistence with the future network protocol; undo/replay.
- **Cons:** replay requires deterministic rules (dice seeds recorded in the log); schema versioning of actions across rule changes needs a story (a version stamp and "discard old saves" is acceptable at this stage).

## Miscellaneous cleanup

- `useGameStore` wrapping `TitanGame` in a Pinia store, rather than a module-level singleton, is justified and not an outlier: a module-level singleton would read `localStorage` at import time, coupling the module to a browser environment; the store gives per-test isolation via `setActivePinia`/`createPinia()`; and it gives the persistence watcher an effect scope to be torn down with. `src/ui/stores/ui/preferences.ts` follows the same shape for the same reasons.
- Done: the global `Object.prototype.guid` extension and `app.config.unwrapInjectedRef` are both gone — `Stack` and `BattleCreature` carry explicit `id` fields that the `v-for` `:key` bindings use directly.
