# State Management

Today: Pinia, with `useGameStore` (`src/ui/stores/game.ts`) holding a `TitanGame` value in `reactive()` — the store state *is* that value, and the nested `Battle` value (`TitanGame.activeBattle`) inherits the same reactive proxying as a field on it. `TitanGame`, `Stack`, `BattleCreature`, `ActiveStrike`, and `Battle` are plain interfaces with their logic in `namespace`-scoped free functions, not classes: `TitanGame.hydrate(persisted?: string)` takes the persisted JSON string as a parameter and merges it onto a fresh `TitanGame.create(2)`; persistence itself lives in the store, not the model layer (doc 05). Every action is a single assert-then-mutate free function (`finalizeSplits`, `finalizeMoves`, `finalizeMusters`, `attackCreature`, ...) — the old `do*`/`m*` pairing is gone — while query functions keep `get*`/`is*`/`can*` naming; the store defines explicit typed getters and actions directly, with no reflection or naming-based dispatch.

## Game state has been separated from game rules (done)

`TitanGame` used to mix serializable state (players, stacks, round) with rules logic (pathfinding, mustering, battle resolution) in one class graph, with reactive proxies wrapping the class instances. `Stack`, `BattleCreature`, `ActiveStrike`, `Battle`, and `TitanGame` are now plain interfaces plus free functions, converted one class per PR in dependency order (`Stack` first, then `BattleCreature`/`ActiveStrike`, then `Battle`/`TitanGame`), deleting each class's hydrate glue as it went. No production code did `instanceof` on a state class, so nothing structurally resisted the conversion.

This works because the state tree was already effectively serializable plain data: every stateful field on `TitanGame`, `Player`, `Stack`, `Battle`, `BattleCreature`, and `ActiveStrike` is a number, enum, boolean, array, or `Record`; entities reference board positions by hex number, never by object; and board layouts, creature stats, and muster tables are static module data outside the state graph (`JSON.stringify` of a game already worked, for exactly this reason). The conversion was "detach the methods," not "re-model the state" — and it buys plain objects for Vue's reactivity (no proxy-vs-class pitfalls), rules that run identically on a server (doc 05), and no more per-class `hydrate` methods.

**`Battle` nesting inside `TitanGame` isn't worth undoing.** Nothing outside `TitanGame` looks up a `Battle` independent of `game.activeBattle` — there's no separate battle store — so persistence stays one `JSON.stringify(game)` call, and doc 05's dispatch model resolves entities by id regardless of where they live in the tree. The friction this used to cause was reactive-proxy nesting (`BattleCreature` sat two proxy levels deep, and Vue's `UnwrapNestedRefs` couldn't reconstruct class-private members, forcing a cast in `BattleBoard.vue`); the plain-interface conversion removed that friction directly, so restructuring the tree on top of it would have bought nothing. `Battle` (`battle/engine.ts`, ~590 lines) is still the largest model file, bigger than `TitanGame` (`game.ts`, ~341 lines) — that's the size of battle rules themselves, not a symptom of the nesting; every one of `Battle`'s functions operates on `Battle`'s own state.

`activeBattle` being a single field rather than a keyed collection isn't a settled property of the domain, though: a round can engage more than one of the active player's stacks at once (`getEngagedStacks` returns all of them), and rule 9.1 has the player choose which to resolve first only after inspecting each. `initiateBattle` is now a separately player-triggered action (#256), letting the player pick from a per-stack list in `TurnPanel` rather than always fighting the first one — but only one battle opens at a time, and `activeBattle` is never cleared once a battle resolves (doc 05's parked end-of-battle gap), so a second engagement in the same round doesn't resolve yet either way. If that gap closes by resolving engagements one at a time — which rule 9.1 requires regardless — a single field stays sufficient; only genuinely concurrent battles would force it into an array or map, and nothing in the rules asks for that.

**Storing a `PlayerId` and resolving it through `getPlayerById` (a linear `find` over `game.players`) is the right pattern — keep it.** `Stack.owner`, `BattleCreature.player`, and `Battle`'s `attacker`/`defender` all hold a `PlayerId`; rendering anything player-flavored (name, color, score) resolves it this way. The lookup frequency reflects the domain — nearly everything on screen renders in its owner's color — and the scan cost is unmeasurable at a five-player cap (`TitanGame.create`'s binding limit is colors, not board size); a `Map` or memoized `Record` would add indirection for no observable win. Some call sites were passthrough ceremony rather than domain-driven, though — a child component demanding a `Player` prop instead of a `PlayerId` — and pushing the id down to the leaf has been cutting those (e.g. `Creature.vue` no longer resolves a player at all).

The id reference is also why persistence works: entities carry ids rather than object references, so `TitanGame.hydrate` can build fresh `Stack`s via `TitanGame.create` and merge persisted data on top with no re-linking step. A denormalized `Player` reference on `Stack` would sever on every restore. (`BattleCreature.playerScore` is the one counterexample — a copy of the owner's score taken at battle initiation, with the staleness semantics a copy implies, unlike the id reference.) `getPlayerById` is now one of `TitanGame`'s free selector functions; nothing about the pattern itself changed in the conversion.

**`Player`'s three fields belong in `TitanGame`, but for different reasons:**

- `score` is rules state and must stay in the state graph — it moved off `Player` onto `TitanGame` (`score: Record<PlayerId, number>`). It feeds titan combat strength (`getStrength`) and tower-teleport eligibility (`canTitanTeleport`). Nothing mutates it yet — end-of-battle scoring is still parked (doc 05) — but once scoring lands, it changes on battle resolution and must replay from the action log.
- `id` is the seat: the `PlayerId` enum doubles as the color, shuffle-assigned at game creation, keying marker art, theming, and every entity's owner field.
- `name` is the one roster field — written once in `TitanGame.create`, never read by rules, only displayed. Under doc 05's authoritative-server model, "who occupies seat X" is session state the server tracks beside the game, resolved by the same `PlayerId`.

The eventual multiplayer refinement is `Player` slimming to seat-keyed rules state while `name` migrates to the roster — not id lookups going away.

## Replace localStorage snapshot persistence with an action log (not urgent)

A snapshot works for solo play but discards history. If actions become explicit data (doc 05's still-pending dispatch slice), persistence could become "store the action log, replay to restore," which also gives undo and post-game review nearly for free. Persistence has already moved out of the rules layer into the store (doc 05's first slice: a deep `watch` on the reactive `game` proxy in `src/ui/stores/game.ts` writes `JSON.stringify(game)` to `localStorage`); an action log would replace that store-side write.

- **Pros:** aligns local persistence with the future network protocol; undo/replay.
- **Cons:** replay requires deterministic rules (dice seeds recorded in the log); schema versioning of actions across rule changes needs a story — a version stamp plus "discard old saves" is acceptable for now.

## Miscellaneous cleanup

- `useGameStore` wrapping `TitanGame` in a Pinia store, rather than a module-level singleton, is deliberate: a singleton would read `localStorage` at import time, coupling the module to a browser environment, and a store gives per-test isolation (`setActivePinia`/`createPinia()`) plus an effect scope for the persistence watcher to be torn down with. `src/ui/stores/ui/preferences.ts` follows the same shape for the same reasons.
- Done: the global `Object.prototype.guid` extension and `app.config.unwrapInjectedRef` are both gone — `Stack` and `BattleCreature` carry explicit `id` fields that `v-for` `:key` bindings use directly.
