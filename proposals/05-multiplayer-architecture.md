# Multiplayer Architecture

Not a proposal to build multiplayer now — a proposal for which modernization choices keep it cheap later. Framework versions verified against npm, July 2026.

## Groundwork worth doing now

Production code under `src/game` imports nothing from Vue, Pinia, or the stores, and — since the persistence move described below — has zero browser dependencies at all. The groundwork decomposes into slices, in dependency order, each shippable on its own — no big bang required.

1. **Move persistence out of the engine — done.** `src/game` no longer reads `localStorage` or calls `window.CompressionStream`/`DecompressionStream` anywhere; `TitanGame.hydrate(persisted?: string)` takes the persisted JSON string as a parameter instead of reading storage itself, and there's no `persist()` call left anywhere in the model layer (the old `game/persistence.ts` file is gone). Persistence is now a single `watch(game, () => { localStorage[...] = JSON.stringify(game) }, { deep: true })` in `src/ui/stores/game.ts`: a deep watcher on the reactive `game` proxy coalesces every synchronous mutation within one action into exactly one write, doesn't fire on initial hydration (the `reactive()` wrap happens after `hydrate()` returns), and doesn't persist partial state mid-action.

   The old `persist()` return value — the compressed/encoded save string — didn't disappear: it lives on as `SystemMenu.vue`'s `persistToClipboard`, a UI-level function that calls `compressAndEncode`/`decodeAndDecompress` from `utils/base64` directly, separate from the watcher's auto-write.

   One behavior change from this move: writes now land on a later microtask instead of synchronously at the end of an action, so `await gameStore.someAction()` no longer guarantees the `localStorage` write has already happened by the time the `await` resolves. Nothing currently depends on that ordering.

   This slice also thinned every action to a single free function: with no `persist()` call left to strip, and no reactive-proxy `this` to close over, the old `do*` (assert + persist) / `m*` (mutate) split had nothing left to justify it — see slice 2 below.
2. **Actions as data, through a single dispatch — payloads converted, dispatch itself not yet built.** Every state change should flow through a serializable action (`{type, payload}`) with a pure/deterministic reducer. This is the same refactor doc 04 recommends, and it *is* the network protocol: local play would dispatch to a local reducer, networked play would send the same actions to a server. Two of the three pieces of this slice have landed; the reducer entry point hasn't.

   **Payloads carry ids, not live instances — done.** `MovePayload`/`MusterPayload` hold a `StackRef`/`MusterChoice`, and the battle payloads (`BattleMovePayload`, `AttackPayload`, `RangestrikePayload`) hold a `BattleCreature["id"]`; each handler resolves the id with `.find(s => s.id === ...)` rather than receiving a live reactive-proxy reference.

   **The `do*`/`m*` split has collapsed into single free functions — done, with one exception.** Every action is now one function: `TitanGame.move`, `TitanGame.setRecruit`, `TitanGame.nextPhase`, `TitanGame.setRoll`, `TitanGame.initiateBattle` in `game.ts`, and `Battle.moveCreature`, `Battle.attackCreature`, `Battle.rangestrikeCreature`, `Battle.assignCarryover`, `Battle.skipCarryover` in `battle/engine.ts` — no `do*` or `m*` name remains anywhere in the model layer. PR #158 (branch `refactor/collapse-store-wrappers`, commit `92d2a9f`) established the pattern for `nextPhase(game)` specifically (inline a single-caller free function into its sole caller, delete the original, rename freely once nothing collides); the same move has since been applied across the rest of the split.

   The exception is `nextPhase(battle)` in `battle/engine.ts`: it's genuinely reused, called recursively from within `engine.ts` itself (the auto-skip logic that fast-forwards empty battle phases) in addition to being called as the phase-advance handler. It stays a separate free function.

   **What's still missing: the single dispatch entry point itself.** There is no `dispatch(game, action)` function and no serializable action union anywhere in the codebase. UI components call the free functions above directly — `TitanGame.move(game, payload)`, `Battle.moveCreature(battle, payload)`, and so on, scattered across `TurnPanel.vue`, `StackPanel.vue`, `Masterboard.vue`, and the battle components. Defining the action union and one `dispatch` function that resolves ids and applies the change is the remaining work; the existing exported functions are nearly a 1:1 inventory of the action types.

   Each action's validation `assert`/`throw` survived the collapse into a single free function; the checks are not uniformly load-bearing:
   - **Load-bearing today** — an achievable UI click sequence corrupts state or misbehaves without them: `setRecruit`'s creature-pool exhaustion check (the muster UI computes choices from `Stack.musterable()` alone and never consults the global pool); `nextPhase`'s engagement-count assert (`engagedStacks.length <= 1`, added in commit `ce7d52d` to fix a Vuex-era version of this same method that silently advanced to BATTLE phase with `activeBattle` left unset whenever 2+ engagements existed; today's code sets `activeBattle` for the first engagement instead, but still silently drops every engagement after it — the stack involved advances toward MUSTER still stacked with an unresolved enemy); and `moveCreature`/`attackCreature`/`rangestrikeCreature`'s phase checks (`movementFor`/`rangestrikeTargets` are pure board-geometry computations with no phase gate, and the UI's "interactive" highlighting is cosmetic — no `pointer-events` gating backs it up — so a creature highlighted for striking during STRIKE/STRIKEBACK can still fire its movement/attack/rangestrike handler if a matching hex is clicked).
   - **Defensive only, currently unreachable given today's UI call graph** — could be dropped as-is: `move`'s phase check; `setRecruit`'s phase/`canMuster` checks; `setRoll`'s phase/mulligan checks; `initiateBattle`'s check (not reachable from any UI call site at all — internal-only); the `attacker.player === battleActivePlayer` checks (already guaranteed by the deselect watcher on every phase-type change); the `activeBattle === undefined` checks (dead in practice, since `activeBattle` is never cleared — see the parked end-of-battle gap below); `assignCarryover`/`skipCarryover`'s movement-phase checks (carryover state is cleared on every STRIKE/STRIKEBACK exit); and `nextPhase`'s BATTLE-case "Incomplete battle!" assert (unreachable — no UI ever renders a next-phase action during BATTLE phase, the same underlying gap).

   Neither category should just vanish when the dispatch entry point above gets built. Validation-before-mutation is still the right pattern for that eventual dispatch boundary: a server can't trust a network-delivered action any more than today's UI can be trusted to always gate correctly, and most of the "unreachable" checks guard actions a network client could dispatch directly even though no current UI path does — `move`, `setRecruit`, `setRoll`, the strike functions, and `nextPhase` itself all correspond to actions a client would send over the wire. (`initiateBattle` is the exception: once `dispatch` exists, its check belongs in the phase-advance handler as an internal precondition, not a separately dispatchable action, so it stays exactly as reachable — or not — as it is today.) None of these checks depend on class-instance `this` anymore — they already run against an explicit `(state, payload)` pair — so nothing about the checks themselves needs to change when `dispatch` is added; a thrown error carries exactly the structure a return value would — a custom `Error` subclass with a `.reason` field, not yet built — caught once at the dispatch boundary and serialized from there, so there's no capability gap between throwing and returning. A single `dispatch(game, action)` entry point is what would make throwing the right choice: with only one boundary to reach, a nested check — a handler calling a shared helper calling another check, several layers deep — can just throw and let it propagate straight to that one catch, composing for free. A return-based `Result` has no such boundary to lean on; it would need `if (!result.accepted) return result` at every call site chaining multiple checks, all the way up.

   Two gaps in the action surface are now closed as side effects of slice 1; one remains open:
   - `togglePendingSplit` (called directly from `StackPanel.vue`) mutates game state with no action wrapper. Persistence no longer cares: it's a deep watch over the whole `game` proxy (slice 1), so this mutation persists automatically like any other, and there's no longer a code path that changes game state and skips persistence.
   - `nextPhase` calls `initiateBattle` synchronously when advancing out of MOVE with an engagement. This used to race two separate `persist()` calls at the end of each; with `persist()` removed from the engine entirely (slice 1), there's nothing left to race.
   - The `Stack`/`BattleCreature` id counters (`stackIdCounter`, `battleCreatureIdCounter`) are still module globals. `TitanGame.hydrate` builds a fresh `TitanGame.create(2)` (allocating fresh ids from those counters) and then merges the persisted state on top, so a restored save whose ids outrun the fresh counters can still collide with ids allocated afterwards (`Stack.id` is a `v-for` key). Still open; id allocation needs to move into state, or become deterministic from the log.

   Separately, `activeBattle` is never cleared after a battle resolves. End-of-battle resolution (scoring, stack elimination, clearing `activeBattle`) is known-incomplete, deliberately parked work; resuming it once the architecture work above concludes is the natural sequencing. Under the dispatch model it arrives as one more handler.
3. **Extract game logic into a package** (decided: do ASAP — slices 1 and 2 are its real prerequisites). Slice 1 is done; slice 2's dispatch entry point is not, so this extraction hasn't started either — no workspace package exists yet (`pnpm-workspace.yaml` only configures native-module allow-listing, no `packages/` directory). Move `src/game` (plus the dispatcher, once it exists) into a workspace package with no Vue/DOM imports, so a Node server imports the identical rules. A pnpm workspace (`packages/engine`, `packages/client`) is the standard shape.

   Shape the boundary as a client↔server protocol from day one: the UI talks only to a `GameServer` interface (submit action, receive state/events), with two implementations of the same interface — an in-memory one running the engine in the browser for local play, and later a WebSocket one for remote play. Local play is then permanently a one-line transport swap away from multiplayer, and the interface stops UI code from ever reaching into engine internals. The extra cost over a plain extraction is small: the interface is async from the start (local play just resolves immediately) and hot-seat play routes through it like any client.

   The realistic size of this boundary is dominated by the read side, not the dozen write actions: battle components call `Battle` free functions directly (`getTargetedStrike`, `getRangestrike`, `movementFor`, `creatureOnHex`, `rangestrikeTargets`, `engagedWith`, `carryoverTargets`) and read fields straight off `activeBattle` (`creatures`, `terrain`, `phase`, `activeStrike`), and the turn/stack/masterboard components read `TitanGame` fields and free functions (`game.stacks`, `game.activePhase`, `getStacksForPlayer`, `getPlayerById`) the same way — each such call site becomes protocol surface. The read side can migrate gradually behind the interface; it doesn't gate the extraction.
4. **Hidden information audit** (needed, but deferrable — not hard to add once the protocol boundary above exists). Stack contents in Titan-style play are hidden from opponents. A client that holds full game state cannot enforce that. Flag which state is per-player-visible so the eventual server can send filtered views. Not started — no state field or component currently distinguishes public from owner-only information.

**Deterministic randomness is already mostly in place.** `src/game` contains no `Math.random`: strikes take `rolls: number[]` payloads, the masterboard roll enters via `setRoll`, and the one in-engine random need (the starting color shuffle) goes through an injected `Random` seam with deterministic test doubles. What remains is authority-side — whoever is authoritative seeds the rolls and the action log records them — a slice-2/persistence concern, not an engine refactor. (The 3D dice-box animation can still render whatever result the log dictates.)

Each of these improves the single-player codebase on its own (testability, undo/replay, faster typechecking of a Vue-free package), so none is speculative work wasted if multiplayer slips.

## Server model options (for when the time comes)

**Authoritative server, thin clients (decided: the long-term approach).** Server owns state, validates actions, rolls dice, broadcasts filtered views/actions. The only model that handles hidden information and cheating honestly. Turn-based games need no tick loop — a request/response + broadcast pattern over WebSockets is enough.

**Lockstep peer-relay.** Server just relays actions; every client simulates. Minimal server code, but hidden info is impossible and any client desync is unrecoverable. Not a fit for Titan-style stacks.

## Hosting/framework options

- **Plain Node + WebSocket (`ws` or socket.io 4.x), custom rooms.** Most control, most code; the engine package does the heavy lifting anyway. Turn-based scope keeps this genuinely small.
- **Colyseus (0.17, actively maintained).** Rooms, state sync with delta patching, per-client filtered views out of the box — the filtered-view feature maps directly onto the hidden-stack requirement. Con: its schema-class state model would compete with the engine's own state shape; adopting it half-way yields the worst of both.
- **boardgame.io.** Conceptually a perfect match (turn orders, phases, secret state, log/replay) but effectively unmaintained — last release 2022. Study its design; don't adopt it.
- **Cloudflare Durable Objects / PartyKit.** One durable object per game room, WebSocket hibernation, no servers to run; pairs with Cloudflare Pages hosting (doc 02). Con: vendor lock-in and a less conventional dev/test loop; PartyKit itself has slowed since the Cloudflare acquisition, so prefer raw Durable Objects if going this route.
- **Supabase/Firebase realtime-database style.** Fastest to first demo, but authoritative rules enforcement ends up in edge functions anyway, and hidden info via row-level security gets contorted. Better for lobby/matchmaking/persistence than for the game protocol itself.

## Persistence & identity (deferrable)

Games as action logs in any SQL store (SQLite/Postgres/D1) — append-only, replayable. Auth can start as magic links or OAuth via the host platform; nothing in the groundwork above constrains this choice.
