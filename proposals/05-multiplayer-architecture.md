# Multiplayer Architecture

Not a proposal to build multiplayer now — a proposal for which modernization choices keep it cheap later. Framework versions verified against npm, July 2026.

## Groundwork worth doing now

Production code under `src/game` imports nothing from Vue, Pinia, or the stores; its only browser dependencies are the persistence path's `localStorage` reads/writes and `window.CompressionStream`/`DecompressionStream` calls. The groundwork decomposes into three slices, in dependency order, each shippable on its own — no big bang required.

1. **Move persistence out of the engine.** Every `do*` action ends with `await this.persist()` (four in `game.ts`, seven in `game/battle.ts`), which writes `localStorage` from `game/persistence.ts` and reaches `window.CompressionStream`/`DecompressionStream` through `utils/base64`; `TitanGame.hydrate()` also reads `localStorage` directly at startup. Together these are the model layer's only browser dependencies. Snapshot persistence is slated for replacement by an action log anyway (doc 04), so it doesn't belong in the rules layer. Smallest slice; after it the engine has zero browser dependencies.

   The mechanism is a single `watch(game, () => persist(), { deep: true })` set up once in `src/ui/stores/game.ts`. On the repo's Vue 3.5.40, a deep watcher on the reactive `game` proxy coalesces every synchronous mutation within one action into exactly one persist call; it never persists partial state mid-action, and it doesn't fire spuriously on `hydrate()`/`reset()`. `src/game/models/` drops every `await this.persist()` call; `persistence.ts` drops its `localStorage`/`base64` imports entirely; the store adds the one `watch()` call and takes over `hydrate()`'s `localStorage` read as well, so the engine's hydration path takes the persisted string as a parameter instead of reading storage itself.

   Two caveats:
   - `persist()`'s return value — the compressed/encoded save string — doesn't disappear: `SystemMenu.vue`'s "copy save to clipboard" feature still needs it, so it splits into its own export-string function, separate from the auto-write side effect the watcher takes over.
   - Because `persist()` runs synchronously at the end of the action today, `await gameStore.foo()` guarantees the localStorage write has already happened by the time the caller's `await` resolves. A watcher's write instead lands on a later microtask. Nothing currently depends on that ordering, but it's a real behavior change.

   This slice thins `game/battle.ts`'s seven `do*` methods — most are already just `assert` + `m*` + `persist`, so dropping the `persist()` line leaves `assert` + `m*`, ready to merge into one method (slice 2 below carries out the merge). It does not collapse `game.ts`'s four `do*` action methods (`doNextPhase`, `doSetRoll`, `doMove`, `doSetRecruit`): they hold substantial branching directly rather than delegating to an `m*`, so removing `persist()` there removes one line and nothing else.
2. **Actions as data, through a single dispatch** (in progress — battle actions landed). Every state change flows through a serializable action (`{type, payload}`) applied by one `dispatch(game, action)`. This is the same refactor doc 04 recommends, and it *is* the network protocol: local play dispatches locally, networked play sends the same actions to a server. It works against the current class model — doc 04's per-class plain-data conversion trails it rather than gating it.

   The shape, in `src/game/models/actions.ts`:
   - `GameAction` is a discriminated union, one variant per player-initiated mutation. Payloads reference entities by id (`BattleCreature.id`, `Stack.id`) plus plain data (hex numbers, dice rolls), never live object references, so an action crosses a serialization boundary unchanged.
   - Each action has a handler pair: `validate(game, action)`, a pure predicate over the explicit state/action pair returning a rejection reason or undefined, and `apply(game, action)`, run only after validate accepts. `dispatch` returns `ActionResult` (`{accepted: true} | {accepted: false, reason}`) and never throws for an invalid action; the store's `dispatch` wrapper logs rejections. Validation-before-mutation survives from the old per-method `assert`s because a server can't trust a network-delivered action, and most of the checks unreachable from today's UI guard actions a network client could dispatch directly — but the old form (synchronous throws against a mutable proxied `this`) only worked with a single trusted in-process caller.
   - The UI dispatches through the store's `dispatch(action)` — the seam slice 3's `GameServer` interface will formalize.
   - Where id payloads force it, validation is stronger than the old asserts: a rangestrike action names only its target's id, so path legality and hazard adjustments are recomputed from state on dispatch (the old payload carried a caller-computed `RangestrikeTarget` the engine trusted), and carryover assignment checks the target against `carryoverTargets()` (previously only the UI gated this).

   The battle actions (`moveCreature`, `nextBattlePhase`, `attackCreature`, `rangestrikeCreature`, `assignCarryover`, `skipCarryover`) are converted; the `GameBattle` mixin keeps only reads plus `initiateBattle`, which no UI calls (internal to `nextPhase`). Remaining slices, in order:

   - **Deterministic entity ids.** `Stack`/`BattleCreature` ids come from module-global counters, so ids are not a pure function of the action history — a blocker for replaying the same action log in two processes, and a live bug for `Stack`: rehydration assigns persisted ids over freshly-counted instances, so a later split can allocate an id colliding with a restored one (`Stack.id` is a `v-for` key, and becomes an action payload ref in the next slice). `BattleCreature` ids cannot collide in practice (one active battle, ids allocated as a batch at battle creation) but share the determinism problem. Stack id allocation moves into `TitanGame` state; battle creature ids become per-battle indexes.
   - **Masterboard actions.** Convert `nextPhase`, `setRoll`, `move`, `setRecruit`, and `togglePendingSplit` (a free function `StackPanel.vue` calls directly — the last mutation bypassing the action surface; its old persist gap closed when the store watcher replaced per-action persists) to dispatched actions with `StackRef` payloads, dropping the `MovePayload`/`MusterPayload` types that carry a live `Stack`. Depends on the id slice for unambiguous resolution. `initiateBattle` folds into the `nextPhase` handler as a synchronous internal step, removing the fire-and-forget call (its old persist race also disappeared with the watcher). The load-bearing checks port as predicates: `setRecruit`'s creature-pool exhaustion check (the muster UI computes choices from `Stack.musterable()` alone, never consulting the pool) and `nextPhase`'s engagement-count assert (without it, 2+ simultaneous engagements would advance into BATTLE while silently dropping all but the first — no UI yet exists to pick a resolution order). After this slice `TitanGame` has no public mutating methods.

   The strike methods' phase checks were the load-bearing battle asserts — `movementFor`/`rangestrikeTargets` are pure board geometry with no phase gate, and clicking a hex in a selected striker's movement range mid-strike-phase fires the movement handler — and are now validation predicates: that click produces a logged rejection instead of an uncaught throw, with state untouched (browser-verified). Two engine-level validation gaps stay open deliberately, since closing them changes reachable behavior: `moveCreature` doesn't check its destination against `movementFor` (the pending-creature "put back" flow moves a creature to its entrance hex, which `movementFor` never returns), and `attackCreature` doesn't check that the target is engaged with the attacker (the UI only offers engaged targets). Both belong in the predicate layer eventually; the first needs the entrance-recall move modeled explicitly.

   Separately, `activeBattle` is never cleared after a battle resolves. End-of-battle resolution (scoring, stack elimination, clearing `activeBattle`) is known-incomplete, deliberately parked work; resuming it once the architecture work above concludes is the natural sequencing. Under the dispatch model it arrives as one more handler.
3. **Extract game logic into a package** (decided: do ASAP — slices 1 and 2 are its real prerequisites). Move `src/game` (plus the dispatcher) into a workspace package with no Vue/DOM imports, so a Node server imports the identical rules. A pnpm workspace (`packages/engine`, `packages/client`) is the standard shape.

   Shape the boundary as a client↔server protocol from day one: the UI talks only to a `GameServer` interface (submit action, receive state/events), with two implementations of the same interface — an in-memory one running the engine in the browser for local play, and later a WebSocket one for remote play. Local play is then permanently a one-line transport swap away from multiplayer, and the interface stops UI code from ever reaching into engine internals. The extra cost over a plain extraction is small: the interface is async from the start (local play just resolves immediately) and hot-seat play routes through it like any client.

   The realistic size of this boundary is dominated by the read side, not the dozen write actions: battle components call `Battle` methods directly (`getTargetedStrike`, `getRangestrike`, `getBoard`, `getOffense`/`getDefense`) and the turn/stack/masterboard components read engine fields raw, and each such call site becomes protocol surface. The read side can migrate gradually behind the interface; it doesn't gate the extraction.
4. **Hidden information audit** (needed, but deferrable — not hard to add once the protocol boundary above exists). Stack contents in Titan-style play are hidden from opponents. A client that holds full game state cannot enforce that. Flag which state is per-player-visible so the eventual server can send filtered views.

**Deterministic randomness is already mostly in place.** `src/game` contains no `Math.random`: strikes take `rolls: number[]` payloads, the masterboard roll enters via `setRoll`, and the one in-engine random need (the starting color shuffle) goes through an injected `Random` seam with deterministic test doubles. What remains is authority-side — whoever is authoritative seeds the rolls and the action log records them — a slice-2/persistence concern, not an engine refactor. (The 3D dice-box animation can still render whatever result the log dictates.)

Each of these improves the single-player codebase on its own (testability, undo/replay, faster typechecking of a Vue-free package), so none is speculative work wasted if multiplayer slips.

## Server model options (for when the time comes)

**Authoritative server, thin clients (decided: the long-term approach).** Server owns state, validates actions, rolls dice, broadcasts filtered views/actions. The only model that handles hidden information and cheating honestly. Turn-based games need no tick loop — a request/response + broadcast pattern over WebSockets is enough.

**Lockstep peer-relay.** Server just relays actions; every client simulates. Minimal server code, but hidden info is impossible and any client desync is unrecoverable. Not a fit for Titan-style stacks.

## Hosting/framework options

- **Plain Node + WebSocket (`ws` or socket.io 4.x), custom rooms.** Most control, most code; the engine package does the heavy lifting anyway. Turn-based scope keeps this genuinely small.
- **Colyseus (0.17, actively maintained).** Rooms, state sync with delta patching, per-client filtered views out of the box — the filtered-view feature maps directly onto the hidden-stack requirement. Con: its schema-class state model would compete with the engine's own state shape; adopting it half-way yields the worst of both.
- **boardgame.io.** Conceptually a perfect match (turn orders, phases, secret state, log/replay) but effectively unmaintained — last release 2022. Study its design; don't adopt it.
- **Cloudflare Durable Objects / PartyKit.** One durable object per game room, WebSocket hibernation, no servers to run; pairs with Cloudflare Pages hosting (doc 02). Con: vendor lock-in and a less conventional dev/test loop; PartyKit itself has slowed since the Cloudflare acquisition, so prefer raw Durable Objects if going this route.
- **Supabase/Firebase realtime-database style.** Fastest to first demo, but authoritative rules enforcement ends up in edge functions anyway, and hidden info via row-level security gets contorted. Better for lobby/matchmaking/persistence than for the game protocol itself.

## Persistence & identity (deferrable)

Games as action logs in any SQL store (SQLite/Postgres/D1) — append-only, replayable. Auth can start as magic links or OAuth via the host platform; nothing in the groundwork above constrains this choice.
