# Hidden Information Audit

This is the audit [doc 05](05-multiplayer-architecture.md) lists as pending under "Hidden information audit" (groundwork slice 4): which `TitanGame`/`Stack`/`Battle` state must not go to every player's client once a server sits between them. It's descriptive research, not implementation.

The rulebook citations below are section numbers from `assets/reference/titan-rules.md`, the copy of the Avalon Hill rules already in this repo.

## 1. What's genuinely hidden, per the rulebook

**A Legion's creature composition is secret from every other player by default.** Rule 4.5: characters are stacked face down under their Legion Marker, and even if a stack is physically disturbed its characters aren't revealed. Rule 5.2: each of a player's two opening Legions starts with three Creatures and one Lord, secret the same way (the rulebook's own word for this is "confidential"). This is the core secret — everything else in this section is either a variation on it or a trigger that reveals it.

**A Legion's composition is revealed to the opposing player, privately, once the two players examine each other's Legion during the Engagement Phase.** Rule 9 defines an Engagement as starting the moment a moving Legion enters a Land another player's Legion occupies, during the Movement Phase; rule 9.1 places the actual private examination later, in the following Engagement Phase (6.3), where the Mover picks the order to resolve any Engagements from that turn. In the current codebase there's no gap between the two: only one simultaneous Engagement is supported (`TitanGame.nextPhase`'s `assert(engagedStacks.length <= 1, ...)` in `game.ts`), and it moves straight from being detected — two stacks sharing a hex, per `TitanGame.getEngagedStacks` — into `initiateBattle` when the Movement Phase ends. So for a redaction rule today, "the two stacks share a hex" is the trigger; it only needs to become "which Engagement the Mover is currently examining" once multi-Engagement support (already a tracked gap in doc 05) exists.

**A Legion's composition is revealed to everyone once the Engagement is resolved by Battle.** Rule 9.1: characters "are kept secret until they are either voluntarily slain as part of an agreement or concession and turned over to the caretaker, or the Engagement is resolved by Battle which must be conducted in view of the other players." Once Battle starts, there's no more hidden information inside it: rule 10.1 places both sides' creatures on the shared Battleland, and rule 12.3's hit chits track wounds openly on that same board, for as long as the Battle lasts.

**Because rules 9.2, 9.4, and 9.5 all require totaling the losing Legion's character values to add to score, resolving an Engagement without Battle — flee, concession, or agreement — reveals composition too, at least to the winner.** The rulebook doesn't say whether that reveal is broadcast to uninvolved third parties too, or stays known only to the two engaged players and whichever of the scorekeeper (20.2) or caretaker (20.1) record the result. This is a genuine rules ambiguity, not something to resolve unilaterally here — flag it for manual review before a server implementation has to pick a default.

**Which specific creatures move when a Legion splits is never revealed, to anyone, at any time.** Rule 4.3: "players do not reveal which characters they split off." The two resulting Legions' locations and owners are public — they sit on the shared board — but the selection of who went where stays permanently secret. Because an Engagement later reveals only each resulting Legion's current contents, not which creature originally came from where, this stays stricter than the general Legion-secrecy rule above even after an Engagement.

**A specific Lord's identity is revealed only when its presence is the basis for a publicly-exercised ability**, not as a side effect of ordinary secrecy: Tower Teleportation requires revealing which Lord enabled it (8.1); Titan Teleportation requires showing the Legion contains the Titan (8.2); mustering a Warlock requires revealing the Titan in that Legion (18.5).

**Mustering reveals only the qualifying creature(s) shown, not the rest of the stack.** Rule 18.0: "he must reveal to the other players the character(s) that qualifies the Legion to do so." A Legion qualified to muster a Troll via two Ogres only has to show those two Ogres, not its full contents (18.4).

**Everything else is public**, by rule or by construction of a shared board. Legion positions, owners, and count per Land are public: the masterboard is shared, and 4.1 forces a full reveal if a Legion ever exceeds seven characters. Each player's score is kept open at all times (20.2); Titan Power-factor is derivable from that same public score by a fixed formula (19.1). The caretaker's remaining creature pool is public — any player may count it outside their own turn (20.1). Dice rolls and the current phase/turn are inherent to a shared physical board and dice, with nothing in the rulebook treating them as anyone's secret.

## 2. Where today's single-client code already exposes this

None of this is a bug — `TitanGame` is one reactive object rendered by one Vue instance in one browser tab for local pass-and-play, so there's no other player's client to keep it from. The point is identifying what a server split would need to start redacting.

`Stack.creatures: CreatureType[]` ([`src/game/models/stack.ts`](../src/game/models/stack.ts)) holds a Legion's full composition, own or opponent's, with no visibility distinction anywhere in the type or the functions that read it. `Stack.split: boolean[]` — the in-progress selection of which creatures are pending a split — has the same lack of gating, despite 4.3 saying that selection should never be revealed even after the fact.

The UI renders both unconditionally, in two places. [`MasterboardStack.vue`](../src/ui/components/game/masterboard/MasterboardStack.vue) renders any stack's `currentMuster` directly on the board (`v-if="stack.currentMuster !== undefined"`) with no owner check and no hovering required. [`Masterboard.vue`](../src/ui/components/game/masterboard/Masterboard.vue)'s `enterStack`/`leaveStack` handlers fire on hovering any stack in `sortedStacks` (a reordering of `game.stacks`, not a filtered subset of it) — attacker's or defender's alike, with no owner filter. [`StackPanel.vue`](../src/ui/components/ui/game/StackPanel.vue) then renders the hovered stack's full `creatures` array unconditionally, and its `toggleSplit` click handler mutates that stack's `split` array for any stack, checking only the current phase and creature count — the one owner-check expression in the file (`game.activePlayerId === props.focusedStack.owner`) only sets a cosmetic CSS class and gates an unrelated block of muster/split-guide text below the creature list, not the list itself or the split click handler. Hovering an opponent's unengaged Legion today shows its exact contents and lets a click mutate its pending split — exactly what 4.5, 4.3, and 9.1 say should stay invisible outside an Engagement.

Battle state (`Battle.creatures`, `BattleSide.creatures`, both in [`battle/engine.ts`](../src/game/models/battle/engine.ts)) is fully exposed today too, but that isn't a gap: rule 9.1 makes Battle state fully public once `activeBattle` exists, so today's unfiltered rendering already matches what a server-mediated deployment should also send everyone.

## 3. What a server-authoritative split implies

The server holds one canonical `TitanGame` (unredacted, same shape as today) and sends each connected client a per-player view built from it. The redaction is not a single global rule — it depends on which player is asking and, for stacks currently engaged, what stage the Engagement is in.

Most of `TitanGame` needs no redaction at all: `players`, `score`, `creaturePool`, `round`, `activePhase`, `activeRoll`, and every stack's `owner`/`hex`/`marker`/`id` are public per section 1 above and can go to every client unfiltered. `Battle` needs no redaction either, once it exists — send it to every connected client as-is, matching the "in view of the other players" rule. `Stack.recruits`, the per-round record of past muster choices, doesn't need redaction beyond what's already implied by `creatures`: rule 18.0 makes the muster reveal (basis shown, creature received) public at the moment it happens, so logging it is just recording an event that was already public.

The actual redaction surface is narrow: `Stack.creatures`, `Stack.split`, and `Stack.currentMuster` for any Legion not owned by the viewing player and not currently a party to an Engagement with the viewer — computed the same way `TitanGame.getEngagedStacks` does today, by comparing `hex` and `owner` across stacks. `currentMuster` is a pending, still-changeable muster choice. Because the rulebook treats mustering as instant-on-reveal rather than pending, it arguably shouldn't preview to anyone, including via a UI event, before it's finalized. That's the whole redaction rule; it just needs re-evaluating per viewer per stack.

Two ways to build it, given the model layer is already plain interfaces plus free functions (doc 04), not classes:

- **Field-level redaction at serialization time.** A function like `redactStackFor(stack, viewerPlayerId, game): PublicStack` that passes `owner`/`hex`/`marker`/`id` through unchanged and replaces `creatures`/`split`/`currentMuster` with nothing (or `creatures.length`, matching what `MasterboardStack.vue` already renders) unless the viewer owns the stack or is the opposing player in that stack's active Engagement. A second function, `redactGameFor(game, viewerPlayerId)`, would apply `redactStackFor` across every stack in a `TitanGame` and pass everything else through unchanged. Additive — no existing type changes — but every new secret field added to `Stack` in the future has to be remembered at this call site, or it leaks by default.
- **Restructure `Stack` into a public/private split**, joined by `id`, so a server can omit the private half by construction instead of remembering to strip fields. Removes the "forgot to redact a new field" risk, but touches every read site across the codebase (`Masterboard.vue`, `MasterboardStack.vue`, `StackPanel.vue`, `TitanGame`'s free functions, `TitanGame.initiateBattle`'s `toBattleSide`) for a redaction surface that's currently three fields on one interface.

Given how narrow the surface is today, field-level redaction is the better starting point — restructuring is worth revisiting only if the redaction function's special cases grow enough that field-level filtering stops reading clearly.

## 4. Sequencing

This audit is a companion to doc 05, not a replacement — it fills in doc 05's groundwork slice 4 without changing the sequencing doc 05 already lays out for slices 1–3.

It isn't actionable yet: redaction needs somewhere to attach to, and that place is the `GameServer` interface doc 05's slice 3 describes (submit action / receive state) — an interface that's already async and already the seam between local and networked play. Building `redactStackFor`/`redactGameFor` makes sense as the "receive state" half of that interface's contract, implemented first as a full-passthrough no-op for the in-memory local implementation so today's behavior doesn't change until a second, real client exists to redact for.

Before that implementation happens, the open rules question in section 1 — how much of a losing Legion's composition becomes visible to uninvolved third parties on flee, concession, or agreement — needs a deliberate answer, not a default picked by whatever the server implementation happens to do first.
