# Rendering Performance: Measured, Not Suspected

Doc 03 called the board's SVG-heavy rendering "suspected, not measured" to be slow and asked to profile before choosing between staying on Vue, rewriting in Svelte, or moving to canvas/WebGL. This doc reports that measurement, done after doc 04's Vuex → Pinia refactor landed (doc 03 named that refactor as the likely biggest lever).

## Method

Measurements ran against `pnpm dev` (Vite's dev server, unminified, no production build optimizations) driven by Playwright's browser automation (Chromium), interacting with the running app the way a player would: selecting a masterboard stack, then moving it. Game state was seeded directly into `localStorage` (the same mechanism the `e2e/` suite's `fixtures.ts` uses) to reach Move phase without playing through Split first.

Two measurement techniques were used, both temporary and removed before this doc was written — the working tree's `src/` has no diff, so there's no patch or script left to rerun; anyone repeating this measurement adds the same counters back by hand.

- **Recompute counts:** a `window` counter incremented inside each computed property under test (`MasterboardStack.vue`'s `stacksOnHex` and `transform`, `utils.ts`'s `hexTransform`, `Masterboard.vue`'s `sortedStacks`), reset immediately before each interaction, to see how many times each one actually re-evaluates per click.
- **Wall-clock timing:** `performance.now()` bracketing a dispatched click. Because the paint that follows Vue's DOM patch happens asynchronously, the bracket doesn't stop at the synchronous click handler — it waits through two chained `requestAnimationFrame` callbacks first, so the measured interval includes that paint.

`app.config.performance = true` (Vue's built-in User Timing integration) was tried first and produced no marks at all. Vue 3.5's bundler build (`node_modules/vue/dist/vue.runtime.esm-bundler.js`) contains no `performance.mark`/`measure` calls anywhere — grepping the file for `performance` returns nothing. The marks are absent as of Vue 3.5.41; this doc doesn't establish why. A future profiling pass needs either manual instrumentation, as done here, or the Vue Devtools browser extension's own flamegraph, not `app.config.performance`.

## Item 1: `mapGetters`/`mapState` — confirmed moot

`grep -rn "mapGetters\|mapState\|mapActions\|mapMutations" src/` returns nothing. All 30 `.vue` files use `<script setup>` with direct Pinia store reads (`grep -rL "<script setup" src --include="*.vue"` also returns nothing — no Options-API components remain). Doc 04's own status note already said this; this investigation confirms it by direct grep rather than taking the note's word for it. There is no Vuex reflection bridge and nothing left for this item to resolve, addressed as a side effect of doc 04 landing, exactly as doc 03 speculated it might be.

## Item 2: per-component transforms — a real, bounded recompute cost, not the geometry math

`hexTransform()` (`src/ui/components/game/masterboard/utils.ts`) computes a hex's position from `MASTERBOARD` (a static structure — the board layout never changes) using a handful of arithmetic operations and object allocations. Doc 03's item 2 called this "transform objects rebuilt on every dependency touch," as if the geometry math were the cost. Two pieces of evidence say otherwise. First, `HexShape.vue` — which draws the ~96 static hex tiles that make up the board background — calls `hexTransform` from a computed whose only dependency is a static hex id prop that never changes after mount; each of those ~96 calls happens exactly once, at initial mount, and never again regardless of subsequent clicks. Second, in `MasterboardStack.vue`, `hexTransform` is called once per re-run of the `transform` computed, no more — a click that moved a stack and caused 2 re-runs of `transform` (see below) produced exactly 2 calls to `hexTransform`, not a multiple of it. The geometry function itself doesn't fan out; whatever calls it does, and only as often as that caller re-runs.

The real fan-out is in `stacksOnHex` (`TitanGame.getStacksForHex(game, props.stack.hex)`, i.e. `game.stacks.filter(stack => stack.hex === hex)`, in `src/game/models/game.ts`). Vue's reactivity tracks property reads at fine grain, and `filter`'s callback reads `.hex` on every stack in the array to decide the result — so every `MasterboardStack` instance's `stacksOnHex` computed ends up depending on every stack's `.hex`, not just its own.

Confirmed by instrumentation across 3 trials on a clean 2-stack board, each starting from a fresh page load with no stack pre-selected, with identical counts every time: moving one stack to a new hex caused both stacks' `stacksOnHex` to re-run (2 of 2), both stacks' `transform` to re-run (2 of 2, because `transform` reads `stacksOnHex.value.length`), and both `hexTransform` calls that followed from those (matching `transform`'s count exactly, not multiplying it). Selecting a stack, with no hex change, caused exactly one `transform` re-run — the selected stack's own — and zero `stacksOnHex` re-runs, confirming the fan-out is specific to hex changes.

This is a genuine O(N) cost per move, where N is the total stack count, versus an O(1) ideal (only the stacks actually sharing the moved-from or moved-to hex need to know). The magnitude at higher N wasn't separately wall-clock measured — an attempt to seed a 25-stack board and drive a move through it hit an unrelated pre-existing issue (`TitanGame.move` snapping a stack back to its `initialHex` when clicked a second time, which crashed rendering when the synthetic seed omitted that field; a data problem with the test, not a rendering bug, and not chased further since it's outside this investigation's scope). The mechanism itself — 100% of stacks recomputing per move, not a subset — was confirmed directly, so the cost at higher N is an arithmetic extrapolation of that same per-call cost (a cheap array filter, run N times), not an independently measured figure.

## Item 3: `v-memo`/`shallowRef` for hex and stack lists — no evidence of benefit

The masterboard's hex list (`MasterboardHexes.vue`, `v-for="id in hexes"`) reads from `masterboard.getHexIds()`, a static list over a `MASTERBOARD` structure that never changes after load. Individual `MasterboardHex`/`HexShape` components have no per-interaction reactive dependencies beyond the global `fancyGraphics` preference toggle, so they don't re-render during normal play at all — confirmed above by `hexTransform`'s call count only including those ~96 hexes once, at mount.

The stack list (`Masterboard.vue`, `v-for="stack in sortedStacks"`, keyed by `stack.id`) already gets correct keyed diffing from Vue — unrelated stacks aren't torn down or remounted when one stack's data changes. `sortedStacks` itself is a list-level computed (`sortBy(game.stacks, ...)`) that re-sorts on both a hex-changing move and a plain selection change (confirmed: 1 re-run for both interactions tested above), which is expected — sort order depends on which stack is selected, not just on hex positions — and isn't a distinct cost beyond the per-stack fan-out already covered: a single sort over N stacks, not N sorts.

`v-memo` would need to gate on individual computed outputs — transform strings, class objects. Those already change reference on every recompute even when semantically equal. That's more complexity than the item 2 fan-out currently justifies.

## Wall-clock measurement

Three trials of one full move interaction — dispatching a click on a hex, then waiting through two chained `requestAnimationFrame` callbacks so the measured interval includes the paint that follows Vue's DOM patch — took 15.8ms, 16.3ms, and 17.1ms on the 2-stack board, all with identical recompute counts. A separate baseline of the same double-`requestAnimationFrame` wait with no interaction at all, also run three times, took 9.8ms, 16.6ms, and 16.7ms — overlapping the move-interaction range rather than sitting clearly below it. That means the technique can't cleanly separate "the work" from "the two-frame wait" at this scale: the total time from click to confirmed paint is consistently in the same ~16ms range as a single display frame interval (16.6ms at 60fps), which is itself the more useful number — a move reliably lands within about one frame, with no sign of a multi-frame delay or dropped paint, on a 2-stack board in an unminified dev build.

The battle board (`BATTLE_BOARD_HEXES` in `src/game/models/battle/board.ts`) has 27 hexes and at most 7 creatures per side — smaller than the masterboard's ~100 hexes. It wasn't separately timed; this is an assumption, not a measured result, but the masterboard's computed structure (per-component fan-out driven by a whole-array scan) has no reason to behave differently on a smaller list.

## Recommendation

Doc 03's own sequencing was: stay on Vue and migrate to Composition API, then measure, then move to Vapor mode only if the numbers still disappoint. They don't — a representative interaction lands within about one frame on an unoptimized dev build, and the one real inefficiency found (item 2's fan-out) is a cheap array filter run N times, not a cost that scales into visibility at the stack counts this game produces. There's no case here for Vapor mode, a Svelte rewrite, or a canvas/WebGL renderer — doc 03's canvas/WebGL discussion already flagged the board's element count as likely below where SVG breaks down, and this measurement is consistent with that.

Item 2's fan-out is real and could be tightened — e.g. an index from hex to stacks instead of a linear filter, so only affected components' computeds invalidate — but isn't worth doing speculatively: nothing measured here shows it costing perceptible time, and fixing it wouldn't be visible in any interaction a player would notice. If board-scale assumptions change materially, this is where to look first; scoping and implementing that fix is future work.
